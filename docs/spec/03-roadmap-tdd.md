# Shelfhold — Roadmap et méthode TDD (v15, après revue passe 13 et arbitrages du porteur 1 et 2)

> Jalons M0 → M6 (+ « Plus tard »). **V1 = M0 → M3** (tag `v1.0.0` à la fin de M3), **V2 = M4 → M6**. Chaque jalon liste les exigences de `01-cahier-des-charges.md` qu'il **satisfait** (tests verts en CI). Aucune date calendaire : un seul mainteneur ; on avance au rythme des « definition of done », dans une **boîte de temps** par jalon (§1 bis, passe 4).
> Principe directeur (arbitrages A1–A3) : **concevoir large, livrer étroit**. Le modèle et les contrats prévoient Séries, sous-sources, AuthFlow, pages paresseuses, multi-destinations ; seules les briques utiles au pont Suwayomi → Kavita sont livrées en M1 (M1a puis M1b). Le reste est « réservé » avec le jalon qui en aura besoin.
> Shelfhold est **l'atelier** (trouver, demander, récupérer, ranger, exporter) ; Kavita / Kover reste **le lieu de lecture** de la famille (ADR-0020). Le lecteur intégré arrive en M5.

### 1 bis. Budget de temps, vélocité et règle de coupe (passe 4, D1, ENF-GOV-005, ADR-0035)

L'explorateur de la passe 4 (R1) estime la roadmap entière à **~1 100–1 800 h** et la 1.0 à **~650–1 100 h**. ### M1a — Pont minimal Suwayomi → Kavita (passe 4, D1)

**Objectif.** La plus petite chose qui **remplace une automatisation existante** sans perte de données : adopter une bibliothèque Kavita **adulte**, la relier au suivi Suwayomi (mode « toujours actif »), puis faire arriver dans Kavita, normalisé, nommé et scanné, chaque nouveau chapitre suivi, une seule équipe par série, sans troisième copie. ### 4.1 Cycle
1. **Rouge** : écrire le test qui exprime le critère Given/When/Then de l'exigence (nom de test = comportement ; marqueur `@pytest.mark.req("EF-EXP-028")`). L'exécuter et **voir l'échec pour la bonne raison**.
2. **Commit rouge** séparé quand c'est praticable (`test: … (red)`), pour que l'ordre soit vérifiable en revue.
3. **Vert** : le code minimal qui fait passer.
4. **Refactor** : tests verts, import-linter vert ; aucune modification de test pendant le refactor.
5. Un test n'est jamais modifié pour passer sans le dire explicitement dans la PR.

### 4.3 Données de test
- **Fixtures et cassettes synthétiques ou domaine public uniquement** (ENF-LEG-002) : images générées (manifest de hash vérifié en CI), HTML/JSON écrits à la main reproduisant la *forme* des réponses, jamais de contenu protégé ni de capture d'un site tiers.
- Les cassettes sont régénérées par une commande dédiée (`mise run cassettes:record <source>`) uniquement contre des serveurs simulés ou des sources dont les conditions l'autorisent, puis revues comme du code (CODEOWNERS).

### 4.4 Barrières de couverture
- **Couverture diff ≥ 85 %** (`diff-cover`), **globale ≥ 80 %** avec branches (ENF-QUAL-001).
- Une PR qui touche `backend/src` sans toucher `backend/tests` déclenche un avertissement (levable par label `no-test-needed` justifié).
- `ci-success` est l'unique vérification requise par le ruleset.

### 4.5 Règles pour les assistants IA (AGENTS.md / AI_POLICY.md)
- Écrire le test qui échoue d'abord, **montrer l'échec**, puis implémenter.
- Ne jamais modifier ou supprimer un test pour le faire passer sans le signaler explicitement.
- Ne jamais régénérer snapshots/cassettes sans demande explicite ; jamais en CI.
- Respecter les frontières de modules (import-linter) ; pas de nouvelle dépendance sans justification dans la PR.
- Pas de PR autonome d'agent : un humain comprend et assume chaque changement.

### 4.6 Dépendances externes dans les tests
- Suwayomi, lncrawl, Kavita : versions **épinglées** ; tests de contrat sur serveurs simulés à chaque PR ; job nightly contre la version épinglée (bloquant release) et contre `latest` (non bloquant, ouvre une issue en cas de dérive). **Kavita (passe 12, M9)** : matrice nightly **{minimum 0.9.1, épinglée, dernière}** (le minimum est désormais testé : c'est son absence qui a laissé passer `plugin/parse` absent de 0.8.9.x, AA1) ; à chaque PR, test hors ligne de `docs/kavita-routes.md` contre l'`openapi.json` figé de chaque version de la plage ; Kavita de test amorcé sans interface.
- **Limites de test des invariants (passe 12, AA6)** : **I42** (identité amont stable des extensions) n'est exercé que par le contrat et des faux (la CI n'a que la source locale et l'extension synthétique) ; l'hypothèse est surveillée en production par `source.renumbered` ; **I43** se teste par une version Kavita annoncée simulée, sans faire tourner d'image vulnérable ; **I46** : on vérifie qu'aucune écriture de l'index déchiffré n'a lieu (base, fichier, journal), pas le swap ni les core dumps, d'où `RLIMIT_CORE=0` dans l'image ; aucun autre invariant n'est intestable avec du contenu synthétique.
- Huey épinglé `>=3.5.4,<3.6` ; montée de version mineure = rejouer les 6 critères du spike S1.
- Suwayomi : le test de contrat réel de la route de téléchargement (S5) tourne en nightly contre la version épinglée.
- Chaque dépendance critique est simulée **à travers son adaptateur** (ENF-GOV-002) : aucun test n'importe directement Huey, foliate-js ou le client Kavita hors de leur adaptateur.
